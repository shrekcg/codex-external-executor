# 最佳实践与落地场景

这份文档解决两个问题：什么时候应该调用外部 route，以及怎样把一次委派做成可验证、可回滚的小任务。

## 一、推荐工作流

```text
1. 选 Provider 与协议
2. 配置 route
3. 离线校验
4. 文本探测
5. 工具探测
6. 小任务冒烟
7. 安装 route
8. 新会话正式使用
```

不要跳过第 4–6 步。认证成功或 HTTP 200 只说明接口可达，不能说明模型能正确调用工具、持续接收上下文或完成 Codex 文件任务。

## 二、按任务选择 route

| 任务特征 | 推荐做法 |
|---|---|
| 只读扫描、字段核对、格式转换 | 选择成本较低且已通过文本验证的 route |
| 需要修改一个或少量文件 | 先做工具探测，再做范围很小的冒烟任务 |
| 复杂重构、跨模块设计 | 保留给主 Agent 或高能力 route，并要求更严格的复核 |
| 需要完整历史的连续协作 | 先确认 Provider 的上下文与状态能力，不要假设 brief 能恢复全部历史 |
| 敏感代码、个人数据、商业机密 | 优先使用可信官方 API；不确定时不要发送，或将 brief_mode 设为 `off` |
| 第三方中转 | 先确认真实协议、数据保留、计费和工具能力，再使用 `custom-*` preset |

如果用户没有明确指定 Provider，不要擅自把任务切到外部 API；主 Agent 可以继续使用原有工作流。

## 三、任务提示词怎么写

用户不需要提供内部 task name、简报路径或 Agent 关系。一个好的委派只需要包含：

```text
使用 $external-model-executor，让 <route> 完成 <具体任务>。
范围：只允许读取/修改 <文件或目录>。
成功标准：<可观察结果>。
完成后：运行 <验证命令>，返回变更路径和验证结果。
```

例如：

```text
使用 $external-model-executor，让 DeepSeek route 扫描当前项目中的旧模型名称。
只汇总文件路径和行号，不要修改文件；完成后说明扫描范围和结果。
```

或：

```text
使用 $external-model-executor，让 tokendance-deepseek route 在 outputs/ 创建一个 JSON 测试文件。
只允许新增该文件；用 Python 解析校验，返回文件路径和校验结果。
```

## 四、上下文、费用与缓存

- 默认只传递任务相关上下文，不继承整个主对话，减少隐私暴露和无效 token。
- `brief_mode: auto` 是通用默认值；只有已知中转会丢失协作消息时才考虑 `always`。
- 简报是 workspace 明文文件，不能放 API Key、秘密文件内容、无关历史或隐藏指令。
- 固定系统指令和工具 schema 可能命中 Provider 缓存；任务内容、文件差异和简报通常会变化，不应按缓存命中来估算费用。
- 外部 route 的费用与 Codex 主 Agent 的调度、核验费用分开计算。

## 五、验证分级

1. **Configured**：配置可解析，route 可解析。
2. **Reachable**：认证成功，文本探测返回。
3. **Tool-capable**：模型返回合法工具调用。
4. **Codex-capable**：真实子任务能够读取、调用工具、完成限定变更并返回证据。

对外介绍或生产使用时，只把第 4 级称为“已验证可执行”。

## 六、典型落地场景

### 1. JSON/YAML fixture 验证

让外部 route 创建一个小型 fixture，并运行 JSON/YAML 解析器。范围容易限制，结果容易由主 Agent复核，适合首次验证链路。

### 2. 旧模型或配置迁移扫描

只读扫描旧模型名、环境变量名、Provider 引用和文档链接，只输出路径与行号，不修改文件。适合低风险、批量、可重复的工作。

### 3. 局部测试生成

给出一个函数和测试目录，只允许新增一个测试文件；主 Agent 再运行测试并检查断言质量。不要一开始让外部 route 重写整个测试体系。

### 4. 文档整理与翻译

限定输入文档和输出路径，要求保留代码块、链接和标题层级。主 Agent 检查链接、命令和术语，不要只依据语言流畅度接受结果。

### 5. 第三方中转的成本平衡

将低风险、可验证的子任务路由到中转 API，把复杂设计、最终取舍、敏感代码和最终验收留在主 Agent。中转协议变化时，重新运行文本、工具和小任务验证。

## 七、失败时如何处理

- 网关启动失败：先运行 `validate`，检查 JSON、端口、loopback host 和 protocol preset。
- 文本成功但工具失败：不要继续扩大任务，先切换协议适配器或 Provider。
- 子 Agent 收到空任务：检查 brief mode 和上游是否丢失协作消息；不要把完整历史无条件发送出去。
- 结果缺少证据：主 Agent 不接受“已完成”的口头结论，要求路径、差异和验证输出。
- 任务范围变大：停止当前外部任务，回到主 Agent 重新拆分。

## 八、发布与维护建议

- 新增 Provider 时链接官方 API 文档，明确真实协议，不写死 API Key。
- 每个协议转换都应有离线测试；每个新增 Provider 都应有配置、文本、工具和子任务验证记录。
- README 只保留复制即用的主路径，详细兼容性放在 `docs/` 与 `references/`。
- 不要把个人项目路径、钥匙串服务名、私有中转配置或真实模型额度写入公开仓库。
